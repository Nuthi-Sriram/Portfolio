Vault File Manager is a native Windows client that customers use alongside Vault Admin to move files in and out of Vault, and I was the sole engineer on it. There's no one else to route a production issue to and no team to spread ownership across — every bug report, every performance regression, and every security finding on that codebase lands on the same desk, and it's mine.

One of the P2 production issues that came through was an upload resiliency problem at scale: sessions handling 39,000 or more files were failing in ways that smaller uploads never surfaced. A client built for individual files and modest batches behaves differently once it's asked to track tens of thousands of them in a single operation — state that's cheap to hold for a hundred files gets expensive at that count, and failure handling that's fine when one file errors out has to work differently when it might be file number 30,000 of 39,000. Fixing it meant making the upload path resilient at that scale specifically, not just faster in the common case.

Separately, a DLL-hijacking vulnerability was identified in the client — a class of vulnerability where an attacker plants a malicious DLL somewhere the application will load it from instead of the legitimate one, letting attacker code execute inside a trusted process. Remediating it wasn't a single patch; it touched more than 30 libraries across the codebase, each one needing to be checked for how it resolved and loaded its dependencies and corrected where the loading behavior was unsafe. That's the kind of fix that's easy to under-scope if you only patch the library where the vulnerability was first found — the actual work was going through the full set of dependencies methodically enough to be confident none of the other 30-plus had the same exposure.

Being the only engineer on Vault File Manager means decisions like how far to take a fix, or whether a "small" issue is actually the edge of a bigger one, don't get a second opinion before they ship. Both of these issues held up under that: the upload fix had to hold at the scale that broke it in the first place, and the security remediation had to cover the codebase, not just the symptom.
